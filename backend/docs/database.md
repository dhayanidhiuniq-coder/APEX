# Database Foundation and Story 1.3 Schema

This document describes the database foundation and the Story 1.3 Projects and
Tasks schema. **Alembic is the approved schema-change path.** This document does
not define an authentication schema; Supabase Auth remains the identity
provider.

## Configuration

- `DATABASE_URL` is optional. When it is absent or blank, database features are
  disabled and the application starts normally.
- A configured URL must use the `postgresql+psycopg` scheme and include a host
  and database name.
- Configuration is validated at application startup without creating an engine
  or opening a connection.
- An invalid configured URL is logged with a static, sanitized warning. The
  application still starts, but database features must be treated as
  unavailable.
- Database URLs, credentials, driver exception text, and connection details
  must never be logged.

## Application lifecycle

- Importing the application creates no database engine.
- Startup validates configuration only. It does not connect to the database.
- Shutdown disposes any engine created lazily during the application lifetime.
- Shutdown suppresses ordinary disposal failures but never suppresses
  `KeyboardInterrupt` or `SystemExit`.
- Database-backed request routes use the lazy session helper. Database-backed
  authentication and a startup connectivity probe/readiness gate remain
  deferred.

## Migrations

Alembic is the approved schema-change path for backend tables. Do not add or use
Supabase SQL migration files for new backend tables. The existing
`supabase/migrations/0001_create_profiles.sql` is the Story 1.2 auth-side
profiles file and is not modified by Story 1.3.

Run Alembic from the `backend` directory. Offline SQL rendering is safe for local
checks and does not read `DATABASE_URL`:

```text
uv run alembic upgrade head --sql
```

The Story 1.3 revision is:

```text
backend/alembic/versions/20261117_1600_4f6c1d2a9b70_story_1_3_projects_tasks.py
```

The revision was applied to the APEX Supabase staging project on 2026-11-17
using the `postgres` owner role for this one-time schema operation. It has not
been applied to production. Read-only catalog checks confirmed the revision,
both tables, RLS policies, and `authenticated` DML grants. The application must
continue to use the separate least-privilege runtime role, never `postgres`.

Before applying the revision to another environment:

- Select and document the PostgreSQL provider.
- Use a dedicated least-privilege migration role; the runtime role must not own
  schema changes.
- Verify the provider's TLS requirements and connection limits.
- Test migrations against an ephemeral PostgreSQL database.
- Review every autogenerated revision manually.

Schema changes must go through Alembic. Do not call `Base.metadata.create_all()`
or run migrations during application startup.

## Model and migration conventions

- ORM models belong under `apex_backend.db.models` and must be imported in its
  registry so Alembic can discover them.
- Keep Pydantic/HTTP models separate from ORM models.
- Use explicit snake_case table and column names.
- Primary keys, foreign keys, unique constraints, check constraints, and
  indexes use the naming convention defined in `apex_backend.db.base`.
- Name check constraints explicitly.
- Use `timestamptz` for timestamps and store UTC values only.
- Use UUID primary keys. Story 1.3 uses database defaults (`gen_random_uuid()`)
  for new rows and UUID foreign keys that match Supabase Auth user ids.
- Specify foreign-key `ondelete` behavior explicitly.
- Avoid PostgreSQL native enums initially; use check constraints or lookup
  tables for migration-friendly evolution.
- Keep revisions linear with one head unless branching is explicitly approved.
- Review and test downgrade behavior, or document a deliberate irreversible
  decision.

## Story 1.3 schema and ownership

The revision creates two tables in `public`:

- `projects`: `id`, `user_id`, `title`, `description`, `created_at`.
  `user_id` references `auth.users(id)` with `ON DELETE CASCADE`, the title has a
  1–120 character check constraint, and `ix_projects_user_id` supports ownership
  lookups.
- `tasks`: `id`, `project_id`, `user_id`, `title`, `priority`, `status`,
  `created_at`. `project_id` references `projects(id)` and `user_id` references
  `auth.users(id)`, both with `ON DELETE CASCADE`. `ix_tasks_project_id` supports
  project lookups. Check constraints restrict priority to `low`, `medium`,
  `high` and status to `todo`, `in_progress`, `done`.

Both tables enable Row Level Security. The projects policy requires
`auth.uid() = user_id` for both `USING` and `WITH CHECK`. The tasks policy
additionally requires the referenced project to belong to the same user. The
revision grants `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on both tables to the
`authenticated` role. It does not grant ownership, DDL, or `BYPASSRLS`.

The FastAPI routes are:

| Method | Path | Description |
| ------ | ---- | ----------- |
| `GET` | `/api/v1/projects` | List the caller's projects |
| `POST` | `/api/v1/projects` | Create a project owned by the caller |
| `DELETE` | `/api/v1/projects/{project_id}` | Delete one of the caller's projects |

Ownership always comes from the verified bearer token. The repository filters
list and delete operations by `user_id`, and request bodies reject extra fields
such as `user_id` or `owner_id`. Query parameters cannot override ownership.

The dashboard lists, creates, and deletes projects through Server Actions. It
includes responsive empty, loading, and error states.

## Supabase RLS runtime model

Story 1.3 runs SQLAlchemy queries with the signed-in user's verified identity so
the existing `auth.uid()` policies are enforced by PostgreSQL for API traffic,
not only by the repository filter.

For every request that uses the SQLAlchemy session:

1. `get_current_identity` verifies the bearer token. The Projects repository
   dependency converts the verified `sub` to a UUID before it builds SQL.
2. Before the repository can issue a statement, the session registers an
   `after_begin` hook. On every new transaction, including transactions opened
   after commit, rollback, or `refresh`, the hook runs:
   - `SELECT set_config('request.jwt.claims', :claims, true)` with the verified
     subject as a bound JSON parameter (`sub`, `role=authenticated`,
     `aud=authenticated`);
   - `SET LOCAL ROLE authenticated`.
   Both are transaction-local. PostgreSQL resets them at commit or rollback, so
   a pooled connection cannot inherit a previous user's identity.
3. If the hook cannot run, the protected statement fails and the API returns a
   sanitized `503`. There is no fallback to the table owner, a `BYPASSRLS` role,
   or repository-only filtering.

RLS is therefore enforced on the API path as well as on direct Supabase access,
while the explicit `user_id` filters remain as defense in depth.

### Database roles and grants (owner prerequisite)

Two distinct roles are required. Credentials are supplied by the owner through
the deployment environment and are never committed to the repository.

- **Migration/owner role.** Used only by Alembic and other DDL. It owns or can
  alter `public.projects`, `public.tasks`, and `public.alembic_version`, and it
  can grant privileges. It must not be the application runtime role.
- **Runtime login role.** Used by the FastAPI `DATABASE_URL`. It must:
  - be a member of Supabase's `authenticated` role so the transaction-local
    `SET LOCAL ROLE authenticated` succeeds;
  - not own `public.projects` or `public.tasks`;
  - not be a superuser and not have `BYPASSRLS`;
  - be allowed to connect through the chosen direct or pooled endpoint.

The revision grants the DML privileges to `authenticated`, so the runtime role
needs no direct table grants. The owner must establish role membership outside
this repository, for example with the migration/owner role:

```sql
GRANT authenticated TO <runtime_login_role>;
```

Do not grant table ownership to `authenticated`. `ENABLE ROW LEVEL SECURITY`
does not constrain a table owner; if the owner must also be constrained, review
`FORCE ROW LEVEL SECURITY` separately because it also changes migration access.
Verify that `authenticated` has `USAGE` on schema `public` and `EXECUTE` on
`auth.uid()` (Supabase supplies both by default).

The staging runtime role is `apex_runtime`. Catalog checks confirmed that it
can log in, is a member of `authenticated`, is not a superuser or `BYPASSRLS`
role, and does not own the Projects tables. A successful runtime database
connection has not yet been confirmed; the current session-pooler connection
is still being diagnosed. Keep its credential in the local backend environment
file and do not put it in source control or chat.

`SET LOCAL` is transaction-scoped, so the model is compatible with
transaction-mode connection pooling. The owner must still confirm the pooler
mode, TLS mode and CA, and connection limits. Session-level `SET` commands must
not be used for request identity because they can leak across pooled requests.

### RLS verification status

The local tests prove that claims and role setup are registered before the first
protected query, re-applied for each transaction, fail closed when setup fails,
and are isolated per session. They use fakes and in-memory SQLite; they do not
prove that a live request is isolated by Supabase RLS. Staging catalog checks
confirmed that both tables have RLS enabled, both ownership policies exist, and
the required DML grants are present. Runtime connection and two-user RLS
behavior remain unverified.

## Verification

Run these local, database-free checks from the repository:

```bash
cd backend
uv run pytest

cd ../frontend
npx tsc --noEmit --incremental false
npx eslint "src/app/(protected)/dashboard" src/lib/backend-api.ts src/lib/project-state.ts src/lib/projects.ts
npx next build
```

The backend suite covers ORM metadata, the Alembic revision contents, API
validation, authenticated ownership filtering, cross-user delete rejection,
transaction-local claims and role setup, setup failure, per-session isolation,
and sanitized persistence errors. The RLS tests use fakes and in-memory SQLite;
they create no PostgreSQL connection. The Alembic scaffold tests render offline
SQL only. The frontend typecheck, focused ESLint check, and production build also
pass.

The following are **not** verified in this environment and must be completed
before claiming Story 1.3 done:

- A successful FastAPI database connection using `apex_runtime`.
- RLS isolation with two real users through the API, the Supabase REST API, and
  direct SQL, including commit/rollback and pooled-connection reuse.
- Production deployment and smoke verification.
